A skill that helped last month may not help today.

Skills are the SKILL.md files that teach AI agents your conventions: code-review discipline, commit style, writing rules. Tens of thousands are shared publicly, and almost none are re-tested when the model underneath them changes.

Driftproof re-runs an agent skill's own eval suite across model versions, samples the judge so every score carries a confidence band, and only claims a regression when the bands actually separate. The phenomenon is the story: verdicts age because the substrate moves.

What it does

For each skill, Driftproof runs its eval suite with the skill and without it, on two model versions. Each response is judged several times, so a case carries a mean ± stddev band rather than one fragile number. Diffing two runs yields a drift report: a case only counts as regressed or improved when its two confidence bands do not overlap. Everything is recorded in a hash-verified receipt — a dated record anyone can re-run — whose every hash is verifiable. Signing is roadmap, not a property these receipts have.

What the band covers, and which band it is. A legacy verdict rests on one generation draw per arm, so its band is the spread of the judge re-scoring that single response, not the spread of the model writing a different one. Report #006 measured the second directly and found it larger. Receipt spec v0.5 samples the generation too, and a v0.5 per-case band is the across-draw spread: the sample standard deviation of the per-draw means, over n draws of that arm. Measured that way, draw-to-draw spread reaches sd 0.355 on the 0–1 scale, on the semver-hidden-breaking-change baseline arm of git-workflow-and-versioning at claude-sonnet-5. The two are different statistics, a band now carries which one it is, and a surprising single-draw verdict is provisional and worth re-running.

Why band-based

An LLM judge is noisy. A tool that cries wolf on that noise is worse than useless. Driftproof's core rule is that a verdict is claimed only on non-overlapping bands — so the honest answer is allowed to be "nothing moved beyond the noise." That restraint is the point.

Latest report

What happens when you fix the instrument and measure the same thing again? Report #007 re-runs three cells Report #005 published, on the same suites and the same substrates, with the generation sampled adaptively instead of once and with the call timeout the surface policy declares. No cell separates: every lift is smaller than its own band (+0.055 ± 0.111, -0.002 ± 0.167, +0.131 ± 0.157), and the 21 cases read 3 improved · 0 regressed · 18 no effect · 0 not measured. Five of six comparisons against the archive were refused before a verdict existed, so the lower numbers are not offered as corrections. The defect it reports is its own: a declared 300 s timeout had been shadowed by a 120000 literal since 2026-07-27, and the truncated run that caused measured less variance than the clean re-run, which is the direction that makes an instrument look more precise than it is. Both runs are published, the broken one as evidence.

Previously — what happens when the skill's own text moves? Report #006 holds the model, the surface, the suite and the judge still and changes only the skill — and it did not get to an answer. 3 cells, 0 measured, 3 refused: each was blocked by its own baseline control, the no-skill arm a revision cannot touch, which failed to reproduce the arm #005 measured. A 120-call stability probe then found why — the baselines are single draws from wide distributions, and generation-level noise runs 3.2× and 7.5× larger than the judge-level noise this instrument samples five times. No cause beyond that is asserted; the control proves non-reproduction and cannot say why. The report publishes the refusal instead of a verdict it cannot support, and three cells in #005 now carry an amendment saying what their baselines rest on.

Before that — what does a skill cost to run? Reports #001–#004 asked whether a skill still helps while something moved underneath it. This one holds that question and adds the half a reader needs before adopting: the same 10 eval suites (Report #001 v1.2 rubrics) and the same fixed judge, across three substrates (claude-sonnet-5, claude-fable-5, gpt-5.6-sol), reporting accuracy lift, token cost and latency side by side and never combined. Report #005: of 30 skill × substrate pairs, 20 separated by at least one case (18 with an improving one, 2 with only a regressing one), and 14 cleared the effect floor on aggregate — 10 carry a price, 4 report a saving, having improved quality while reducing cost. The measurement itself cost 9.2× its projection, and the report says so on the page.

Before those — Report #003: two versions of one model (claude-opus-4-8 → claude-opus-5); 4 improved, 2 regressed (both single-case, one exactly on the floor), 4 within noise. Report #002: the same suites across two vendors' CLIs — 3 durable, 4 substrate-dependent, 2 regressed, 1 no-effect. Report #001: the first release-drift study, on a Sonnet pair; 9 of 10 moved beyond noise.

Driftproof publishes six report types. A release drift report (#001, #003) asks whether a skill's verdict holds when the model version underneath it changes; a substrate durability report (#002) asks whether it holds across a change of substrate — a different model behind a different vendor CLI; a capability-gap report (#004) asks whether it holds on a higher tier of the same provider; a value report (#005) holds the substrate still and asks what a skill costs to run alongside whether it helps; a revision drift report (#006) holds everything underneath still and moves the skill's own text; and an instrument re-measurement report (#007) moves neither, and re-runs cells an earlier report published on a corrected measuring device. All use the same band-based, floor-gated rule; they differ in what moves underneath the skill — or, in the value report, in which axes are measured.

Run it on your own skill

You need Node ≥ 22 and an ANTHROPIC_API_KEY. From "found the repo" to a receipt for your own skill is about five steps:

npx driftproof init my-skill          # scaffold SKILL.md + evals/evals.json + .driftproofrc
# edit the 3 example cases so each is grounded in a claim your SKILL.md makes
export CLAUDE_PROVIDER=api
read -rsp "Anthropic API key: " ANTHROPIC_API_KEY && export ANTHROPIC_API_KEY
npx driftproof run my-skill --models claude-haiku-4-5
cat receipts/*.summary.md              # read the receipt + human summary

The verdict answers "does the skill still help on this model?" — PASSED when the with-skill score beats the baseline by at least the effect floor, NO_EFFECT when it doesn't, REGRESSED when the skill hurts. Each case is judged several times so it carries a mean ± stddev band, and a case only counts as moved when its bands don't overlap and the mean shifts past the 0.05 effect floor. Full walkthrough in the README quickstart; how to write a fair suite in the authoring guide.

Verification in CI

Wire drift detection into a repo with the GitHub Action (uses: driftproofhq/driftproof@v0.7.1): it re-runs the suite on every push, uploads the receipt, and fails the job if the skill regressed. driftproof badge turns any receipt into a shields.io badge — the one below is generated from the bundled example's own receipt.

Roadmap

  • More reports as the substrate moves — a release watcher polls for new model versions daily and queues a draft report for review when one ships.
  • Signed receipts — a key signature over the canonical form, so a receipt can be trusted, not just read.
  • A sandboxed-execution harness for tool-execution skills (document renderers, diagram/asset generators) that Report #001 scopes out.
