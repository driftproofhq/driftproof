How Driftproof measures a skill

We run a skill's own test tasks with the skill and without it, score every answer several times, and call a change only when it is clearly bigger than the usual spread of the scores.

The full contract is the receipt specification. This page is its plain companion; the precise method, in the specification's own terms, is folded at the bottom.

With and without the skill

For each task in a skill's own test set, Driftproof asks the model twice: once with the skill's instructions loaded, and once with the task alone. The model answers each way several times.

A fixed grader, another model, scores every answer several times. So each task gets a spread of scores, not one fragile number. What the skill adds is the average with the skill minus the average without it.

In short

  • One task, asked two ways: with the skill and without it.
  • Several answers each way, each scored several times.
  • What the skill adds: the average with it minus the average without it.

When we call a change

When two runs of the same skill are compared, a task counts as better or worse only when both of these hold.

First

The spreads are apart

Each side's spread is its average plus or minus the usual variation of its scores. If the two spreads overlap, we do not call a change.

Second

The gap is big enough

The averages must differ by at least 0.05. The grader scores on a coarse grid of about 0.05 to 0.1, so 0.05 is about one step of it. A smaller gap is not called, even when the spreads are apart.

When a change is not called, a report says which of two things it saw. If the scores were so spread out that a gap of 0.05 could not show, or a side had only one answer, there were too few answers to tell. Otherwise the spreads overlapped or the gap was too small, and there was no clear difference. Neither means that nothing changed. A clear difference is what these tests saw, not proof that the skill itself changed.

Extra checks, and what a skill costs

Simple checks beside the grader

A task may also carry plain checks on the answer that simply pass or fail, with no model judging: for example, that a commit message starts with the expected kind of first line.

They sit beside the grader's scores as extra evidence. They never decide whether we call a change.

What the skill adds per 1,000 tokens

A skill is not free: its instructions are sent with every answer. Adding 0.10 with 400 tokens of instructions is a different deal from adding 0.10 with 6,000.

So Driftproof gives what the skill adds both as it is and per 1,000 tokens of the skill. The token count is a rough estimate: the length in characters divided by four.

Other models, and one grader for all

The same tasks and the same grader run for every model we test; only the model answering changes. Every receipt records which model answered, and through which service. Claude Code can make a call of its own on another model; the receipt records that call and its tokens beside the answer, and a run stops when another model gave the answer (the receipt specification).

Because one grader from one model family scores every answer, a report comparing model families leads with what the skill adds to each model. That reduces a grader's taste for its own family's writing, but does not remove it, and no report has measured how much is left. Raw scores across families are background, never a ranking. The neutrality page has the full policy.

Receipts are an open format

A receipt is the file behind every published number. Its format is public and any tool may write one; Driftproof also converts results from neighbouring test tools (see interop).

A receipt records what produced its numbers: the model, the tools, the skill and the tasks by their content, and the grader with its instructions. The stale command compares those with what would run today and says what has moved. With --keep-transcripts a run keeps every answer it was returned, each with the grader's replies to it. Supported non-repository receipts can be regraded with no new answer drawn. A rubric regrade refuses a grader whose recorded setting differs from the original's: its model, service, sampling, instructions, tool version and isolation, the address its calls use and the routing settings they are handed, the code on the grading path, and the dated model it answered as. Some of a grader's setting is not recorded, and so not compared: a command-line grader's own settings files, and the shell profile of the account an isolated grader runs as, among others the receipt specification lists. The regrade counts only the answers that reach the grader, and refuses any input it cannot hold to the original. Originals with no recorded judge identity, and anonymous judge replies, cannot support a rubric regrade. Regrades count logical judge calls separately from runner attempts, including retries and timeouts. A runner attempt is an API request or a CLI invocation; requests made inside a CLI are not counted. It writes a receipt of its own, and sealed in its hash are the original receipt and the runner version that made it, the answers it read, the revised tasks, the original grader, the answers graded and carried, and the calls made. Checks are never run again: a task's check results are kept only for the answer they were run on (the receipt specification).

driftproof run --timeout <seconds> sets the limit for each generation and judge attempt on every surface. Each retry gets that limit. The receipt seals the explicit setting as run.timeout_ms, in milliseconds. It records a configured limit, not elapsed time or a deadline for the whole run. Without the flag, surface defaults stay unchanged and the field is absent. The flag keeps --quick's sampling and UNVERIFIED level (the receipt specification).

A plain judge regrade refuses anonymous judge replies; no receipt is written. Each returned sample must report the requested judge identity. A mixed-model reply must explicitly name the requested judge as serving the reply. Reported ids preserve dates when supplied. The stub exception records UNVERIFIED. An UNVERIFIED original stays UNVERIFIED. Reported identity comes from the reply and does not authenticate provider identity or measure grading accuracy.

Each graded answer seals every returned sample's reported ids and serving id beside the hash of its score text, in reply order. Invalid scores and returned replies beside a timeout keep that evidence too. Aggregate judge ids are unique and sorted in lexical order. Serving identity comes from the reply; token share alone does not establish it. A refusal stops before writing any output. Endpoint attempts are counted when the runner makes them, including retries and timeouts. The stub makes none. Requests inside a command-line tool are outside that count. Answers archives and identity evidence have explicit byte, collection and string limits, checked before parsing archives or copying ids; malformed or oversized input refuses with bounded diagnostics. These bounds cover answers and identity entering regrade, not provider transport buffering or receipt and suite size. The receipt specification gives the limits and evidence fields.

The method in one sentence

Compare sampled answers with and without the subject text, account for their spread and lost draws, and report token use beside the result.

The precise method

The folded sections are the method as the receipt specification states it, in the terms reports and receipts use. They say what the sections above say, precisely.

The precise method, in the receipt specification's own terms

The core: with vs without, sampled, banded

For each eval case, Driftproof runs the model with the skill (SKILL.md supplied) and without it (bare baseline). Judge-primary runs sample a fixed judge. Execution-primary R-2 uses hidden-test pass rates and their spread across generations. The skill's lift (delta) is the with-skill mean minus the baseline mean.

The drift verdict rule (anti-false-positive)

Diffing two receipts yields a per-case verdict. A case counts as regressed or improved only when both conditions hold:

  • Band separation. The two with_skill bands do not overlap. A band is a descriptive spread: the mean plus or minus one sample standard deviation of the case's scores, with no coverage probability.

Where a band comes from

Not enough draws. A case the rule does not separate is also asked whether it could have been separated. Its resolution is the two arms' spreads added together, plus two standard errors of the difference between their means; when that reaches the 0.05 floor, or when an arm has a single draw, the case is underpowered, and a receipt with no separated case and an underpowered one reads UNDERPOWERED, in words: Not enough draws to conclude at this effect floor. The badge, the Action and the comparison report print the draws per arm that would have been needed with the spreads held, or say that no draw count reaches the floor when the spreads alone do, because more draws narrow the standard error and not the spread. The single-receipt badge reads passing or regressed only when a case separated under the rule. The rule is R-1 to R-6 of the receipt specification.

A wide band over several cases. A receipt in which two or more cases read no separation, and none is underpowered on its own, is asked the same question once more, over the receipt as a whole. Its comparison band, each arm's spread of its per-case means added in quadrature, must be under the 0.05 floor. When it reaches the floor the receipt reads UNDERPOWERED, with no draw count, and says what makes the band wide. Each case's mean moves a little from draw to draw, and more draws shrink that part; how far the cases sit apart, no number of draws changes. With the draw-to-draw part taken out of each arm, a band still at or above the floor is the cases disagreeing, and the receipt says More cases, not more draws, are needed to conclude at this effect floor. A band under it is draw spread, which more draws are expected to narrow, and the receipt says Not enough draws to conclude at this effect floor. Where a case lost draws, its band is widened by the most its mean could move at any score those draws could have had, and the receipt says not enough draws. It says the same where an arm measured one draw, or records no spread across its draws (generation.sd): the draw-to-draw part cannot be read from it. A one-case receipt forms no such band and reads as before. The reader applies this rule to every receipt it reads, whatever its schema version.

Lost draws in a diff. A draw the runner could not measure, such as one that timed out, is recorded on the receipt as unmeasured and left out of its arm's mean and spread. So when two receipts are diffed, a case that separated on its measured draws counts as regressed or improved only when it separates at every score either side's lost draws could have had, from the worst score of the judge's scale to the best. When it does not, the diff reads the case inconclusive. Each case that lost draws is named, with each side's lost and drawn counts and the reasons the receipt records, and the per-case table then gives every case's measured and drawn counts.

Lift by case

driftproof view adds a breakdown to each receipt sheet. driftproof diff --lift-breakdown adds separate breakdowns for the two receipts. Without the flag, diff output stays unchanged. Each breakdown uses only recorded draw scores sealed by that receipt's hash. It shows each case's with-skill and baseline means, sample spread across answers, their difference, and measured, drawn and lost counts. The spread is the sample standard deviation of measured draw means. Extra judge samples are not separate answers. Lost draws are left out of these means and spreads.

Each included case has equal weight in the measured lift. Removing a case removes both arms and recomputes their means from the remaining cases. When evidence and eligibility permit, a case carries the positive measured lift only when the full lift is positive and removing it leaves zero or negative lift. This decision precedes reporting rounds. It describes the recorded scores at this sample size. It predicts neither future answers nor a causal mechanism.

Helps and hurts mean upward and downward separation under the existing effect floor and sample spread rule, including lost-draw protections. The breakdown lists the cases that separate downward. Comparative labels require the same exact recorded grader in both arms and the run, and the same non-null rubric hash. Lost draws prevent a carrier assertion. Below-TESTED, smoke, incomplete, narrowed or non-model receipts carry no helps, hurts or carrier assertion.

Unavailable results carry reasons. Failed arms are excluded together and remain visible. Missing draw evidence on an included case makes the suite lift and every omitted-case lift unavailable. Legacy judge samples cannot replace draw evidence. Invalid hashes, malformed evidence, contradictory draw counts and unsupported sizes cannot supply a breakdown. A receipt over a size limit keeps its sheet and its diff report; only its breakdown reads unavailable, naming the limit. There is no model call, receipt edit or new receipt field. Existing verdicts, bands and published numbers stay unchanged.

Existing UNDERPOWERED wording stays Not enough draws to conclude at this effect floor, or, when the cases disagree under the existing rule, More cases, not more draws, are needed to conclude at this effect floor. Neither sentence means equality or absence of an effect.

Which answer is graded. On the two command-line surfaces the model answers as an agent with tools. From receipt v0.10 on, the receipt says which answer the grader saw, in run.capture. By default, text, the agent has no tool that writes a file or runs code, and its reply is the graded answer. On Claude Code it keeps only the tools that read, Read, WebFetch and WebSearch, named in an allow list, so every other tool is off, PowerShell and REPL included, and so is any tool a later version adds; no MCP server is loaded. On Codex the sandbox is read-only and every feature its own feature list names that writes a file or runs code is turned off, the shell among them, with no MCP server. With --capture files it may write files in a fresh working directory of its own, with the file tools Write, Edit and NotebookEdit added on Claude Code and still no tool that runs code; on Codex the sandbox lets it write in that directory, with its features as they are. Every file it leaves there is named in the graded answer with its path and size, and so is a directory there that cannot be read, with its reason; the first 50 files are read: each is graded with its reply when it is UTF-8 text of at most 65536 bytes, up to 262144 bytes together. Any other file is named with its reason: past the 50-file cap, truncated (its size and the cap), unreadable (permission denied, or a read error), binary, not valid UTF-8, changed while it was read, or past the total cap. Each draw lists them in captured_files. A model that writes its answer to a file and replies with nothing is graded on the file. When it replies with nothing and no file it left can be shown, the draw is lost, its files are still listed, and its reason names them with theirs. When the directory could not be read back, the draw is lost, and a regrade keeps it lost. In text/files capture, a reply that points at a file the answer does not include, or that only describes work it did, is a lost draw with its reason and is never given a score. A draw is lost only when it truly points at a file the grader was not shown, or holds no answer. So a line inside a fenced block is never read as the model pointing at a file; a commit body or pull request description that lists the files it changed is graded; a pointing line followed by a fenced block, or by at least 200 characters of the reply's own prose, shows its file, so a summary written to a file and then given in prose is graded on the prose, and prose on the pointing line itself counts; a pointing line below the reply's own answer shows its file too: at least 200 characters of prose above it, a fenced block above it that the line refers back to ("I saved this to ..."), a Changes list under the answer, or the body of a commit message; a code name such as cart.total is not a file name; first-person advice such as "I'd add an index" is an answer, not a report of work. A typographic apostrophe or quote mark reads as a plain one, and a file name in bold or other emphasis, or after a bold label such as Created:, reads as a file name. On these two surfaces the runner also records the harness in run.harness: its name and the version its own binary printed when the run began, never a typed value. A regrade keeps the original's mode and harness, because the answers it grades came from that harness, so driftproof stale still reads the version the answers were made with.

Repository capture

Live repository runs use the Claude subscription CLI with coding tools in a confined copy of a pinned starter. The judge sees the reply and captured text changes, with omissions disclosed. A character annotation distinguishes Unicode and control characters without changing source bytes. It is a reading aid, not a guarantee of correct judgment. Receipts distinguish available tools from observed calls and results; stub runs provide no execution or isolation evidence. Repository receipts cannot be regraded.

R-2 uses hidden-test pass rates for 19 tasks. Sonnet grades test quality separately; TypeScript stays judge-only outside that aggregate. Primary statistics and adaptive stopping use execution scores, without blending in secondary grades. The judge is instructed to assess tests without credit for unsupported execution claims. Recorded Unicode misreadings and a false positive on contradictory tests remain disclosed limitations.

Smoke admission requires complete measurements and passing controls. The full-run audit may continue with disclosed draw losses, leaving scores and sealed INCOMPLETE status unchanged. Systemic failures and primary losses above the allowed limit still stop it. See the receipt specification for that rule and the retained evidence.

driftproof run uses the call and spend defaults in config.js. The R-2 smoke and full-run drivers use call caps without a dollar budget. Full-run jobs are serial by default, with up to four jobs concurrently; calls within each job stay serial. Jobs share the subscription and box, so wall time and retry counts are not comparable to a serial run.

Checkpoint, pause and resume

A file named pause in the output directory requests a stop before the next call. The runner saves completed phases and exits 75; a draw may be partly judged. Compatible resume reuses finished draws and saved samples. Undispatched or interrupted samples may have no saved reply. Completed receipts recover without calls. Keep the whole output directory. See the checkpoint contract for compatibility checks and the pinned orchestration exception.

A smoke run gives no verdict. driftproof run --quick is a first look: it runs one test task, the first in the suite, and no other, to see that the skill and that task run, with 2 draws per arm, 2 judge samples per answer and concurrency 4, and shows that task's answer with the skill and without it side by side. That is too few answers and too few test tasks to give a verdict, and the receipt says so. From receipt v0.11 on, a quick run records run.preset as quick and reads UNVERIFIED whatever answered it, and the schema refuses a receipt that names a preset and reads TESTED. Every reader of a verdict refuses a receipt below TESTED, so the badge, the Action's decision and the comparison report give a smoke receipt none. The comparison report counts a receipt that names a preset as below TESTED whatever level it carries, so a smoke receipt restamped TESTED and sealed again is refused as an honest one is, and the report names that side as a smoke run. The Action's decision writes its lift as n/a in its summary and in its workflow output, and the badge writes it as n/a in its workflow output. The comparison report, the badge's JSON and the exported summary keep the lift, with its plus or minus sign, as context, as they do for every receipt below TESTED. The plain words and the results page label it Smoke run, no verdict: a smoke run cannot produce a verdict, and a run without --quick can.

Figures a source printed give no verdict. Some sources publish aggregates only: one score and one uplift per dimension and agent, with no per-run score. From receipt v0.13 on, an import from such a source, NVIDIA's skill benchmark cards today, carries the figures as the source printed them in source_figures, with the repository, the commit and each file's git blob sha1, beside the mark uncertainty_unavailable: "aggregates_only". Its case rows carry no score and its comparison is null. Every reader of a verdict reads the mark where it reads the verification level, so the badge, the Action's decision, the comparison report and the view give such a receipt no verdict, no band and no lift, and a regrade or a plan refuses it. Where a card prints an uplift with no unit, the unit stays unstated and no baseline is worked out. Driftproof records the files and the commit it read; it does not attest the author.

What grading cost. Each receipt discloses the grader's cost in economics.judge_overhead, apart from every figure about the skill. Each case's answer is generated several times, so the cost is counted over every draw the grader was sent, each once, at the grader's price frozen in the receipt. It prices reported answered-sample usage at frozen API rates. Dollar figures for subscription runs are estimates, not a bill. Retried attempts and unreported usage are excluded. Repository summaries separately sum surface-reported amounts and count unknown costs; these are subscription accounting, not charges or remaining allowance. The receipt says how many draws it counted, in judged_draws_counted, and how many had no usage to count, in judged_draws_missing_usage. A draw a regrade copied from the original, because it could not be graded, is not counted. A receipt with draws that records no judged_draws_counted counted one draw per case; the receipt specification dates the correction and says how to count its draws.

A comparison report's headline says no separation detected when no case separated under the rule, and names the direction of each separation it detected. A comparison report names the band source of each receipt beside its bands, legacy or generation, and its legend describes only the sources that appear on the page. It prints the sentence that the two receipts' bands come from different sources, and that a per-case comparison across them is not like for like, only when the two sources differ. Two receipts whose bands share a source are compared without that sentence.

Deterministic post-checks (supplementary column)

A suite case may declare optional checks[] - structural or regex assertions on the model output that simply hold or don't, with no LLM judgment (e.g. "the output contains a Conventional-Commits subject line", "the output mentions the 429 status the task described"). These run alongside the judge and are reported as a separate column.

Post-checks are supplementary evidence only. They are not folded into the case outcome or the band-overlap verdict - they corroborate or contradict the judge with a cheap, unambiguous signal, they do not replace it. Authors add them where they are natural and in-text-groundable; they are never required, and a suite without them is unaffected. Each result is recorded in the receipt as { name, kind, pass } (spec v0.3.1).

A case may also list weighted criteria in place of a free-text rubric, at most 50 criteria, each description bounded as a rubric is. The grader then decides each criterion, met or not met, and the weighted total and the pass are computed in code, never taken from the grader; a reply that does not decide every criterion, each with a reason that holds a letter or a digit, is not measured (the receipt specification). A case with neither a rubric nor a criterion object, an empty criteria list among them, is refused before any call. That pass is per sample: the case outcome still comes from the mean and spread of its scores against the threshold, as for every case, so a mean exactly at the threshold reads borderline. This fixes the arithmetic, not the grader's reading of an answer. Each criterion's id, weight and description enter the case's rubric hash in the receipt, with the criteria template as the grader reads it, so an edit to any of them, or to how a criterion is shown to the grader, moves that hash.

The value-per-token axis

A skill's subject text is sent with generation calls. Each receipt page, skill index row, skill measurement result, decide job summary and driftproof view page states the skill's token cost beside its result, read from that receipt alone. The run console, regrade summary and diff CLI also state that cost beside lift. Diff reads each side separately and forms no cost difference. Ordinary run summaries, library drift reports, the badge, the Action outputs and published report bodies carry no cost.

The figure. For each of the two arms, with the skill and without it, Driftproof takes the mean input tokens and the mean output tokens per generation call over the arm's measured draws, as the answering surface reported them, each mean rounded to two places and then to a whole token. Both steps round half up using integer quotient and remainder, so a binary division cannot move a boundary. The cost is the with-skill figure minus the without figure, input and output apart, so it is the difference of separately rounded arm means: means of 10.4 and 5.6 tokens give a cost of 4, not 4.8. Grading is not in it, and nor is a placebo arm. Both arms use the same harness configuration; its contribution need not cancel across different tool trajectories.

When there is no figure. A draw with missing usage or a missing token count leaves its arm with no figure, and nothing is averaged over the rest. A present invalid or out-of-range count refuses the cost, with no estimate. A receipt whose seal does not verify, or whose usage is outside the limits the reader holds, states no figure. The first applicable rule wins: an invalid seal states no figure; a sealed stub run states its cost as simulated, with no figure; then aggregates-only and publication scope restrictions suppress cost; then usage limits and measurement are read. A receipt that does not record a model answering, or whose arms form no figure, gives the estimate below, named as one, or says the cost was not measured. No lift-per-token ratio is printed beside a verdict: a ratio over a banded quantity would read as a ranking the band rule does not support.

The publication scope restriction applies to the delegated-skill records named by the Report 015 amendment.

The estimate. skill_tokens is a coarse ceil(chars ÷ 4) estimate of the subject text length - the standard rough proxy for English text, not a model tokenizer (no tiktoken dependency). For a skill directory the estimate names SKILL.md. For a context file it says subject text length. It is a consistent yardstick, not a billing figure, and it is recorded in the receipt (skill.tokens, spec v0.3.1).

Providers, surfaces, and neutrality

Driftproof's provider layer is two-axis: provider (anthropic / openai) × surface (api / cli), i.e. four concrete lanes. Each comparison holds the judge fixed across its arms. A report records its suite, target models and judge configuration. Every receipt records the provider and surface it ran on, the API surface is preferred for published runs, and a subscription CLI surface is disclosed whenever used.

When one Claude-family judge grades every provider's output, a cross-provider report leads with the with/without delta - which reduces judge style-affinity but does not remove it - and treats absolute cross-provider scores as context, never a ranking. Report #002 additionally holds the surface type constant: both substrates run on the vendor's own first-party subscription CLI (claude -p and codex exec), with each surface's harness overhead disclosed (Codex prepends a fixed ~12–15k-token preamble; claude -p a smaller first-party context). The full policy is on the neutrality page.

R-2 judge configuration. Sonnet 5.5 judges both Haiku 5.5 and Sonnet 5.5, replacing the historical crossed pairing. Comparisons are within one target across baseline, with-file and placebo. Sonnet self-grading may favor its own model; receipts and reports disclose this limitation.

Related work

Skill Drift Is Contract Violation (Fan et al., arXiv:2605.10990) treats skill decay as a violation of environment contracts - external services and APIs moving under a skill - and repairs against them; that environmental axis is complementary to the substrate axis measured here (the model itself moving under a skill). The verification levels our receipts carry (UNVERIFIED / DECLARED / TESTED / FORMAL) follow the lattice introduced in Skills as Verifiable Artifacts (Metere, arXiv:2605.00424), whose companion, Methods for Formal Verification of Agent Skills (arXiv:2605.23951), works toward the FORMAL level our schema still marks reserved.

Receipts are an open format

The receipt is not proprietary: the JSON Schema is served at its canonical id (/spec/receipt.schema.json), and a receipt validates against the schema its own schema_version names. Driftproof writes receipts at the current schema version only, and a receipt at an older version stays readable, checked against its own; any harness is encouraged to emit receipts, and working converters import results from neighboring eval tools - with the DECLARED vs TESTED distinction enforced structurally (imported declarations are recorded faithfully but never earn drift verdicts). The schema, the import mappings, and the minimal summary-json interchange are on the interop page. A receipt at the current schema says what its counts count: generations per arm and judge samples per generation are separate fields, written only at the scope the data establishes, and an imported receipt carries neither unless its source format defines one. Where a count is not established the differ and the export say it is unknown; they do not read it as a single sample. An imported receipt at the current schema also names what produced it: the harness and its version, the document it was converted from with that document's sha256, and each thing the source did not record, which stays unknown rather than taking a default. Where the source ran a skill-fired indicator, as claude plugin eval does, the receipt records how often the skill fired beside the score and never inside it, and runs the source recorded an error for are kept out of the figures and listed with the error.

A receipt also records what produced its numbers, as far as its schema version allows: the model, the harness, the capture mode, the skill's and the suite's content hashes, the judge, the judge's prompt template and each case's rubric hash. driftproof stale compares those with what would run today and says, for each arm, whether the result still stands, needs the arm run again, or needs only its saved answers graded again. A change to the skill leaves the baseline arm standing, since that arm contains no skill text. A new major or minor version of the harness means running again; a patch release of the same harness is reported as an advisory. A different capture mode also means running again, because a different answer would be graded. For scale, from our own runs: Report 009 ran on Claude Code 2.1.272 on 15 September, and on 23 September Report 011 needed 2.1.280 or newer. Anything a receipt does not record is reported as unknown, never as current.

Sample the judge, band the scores, require separation and a real-sized effect, add cheap deterministic checks on the side, normalize lift by the tokens it costs, and hold everything constant except the model. That is the method.
